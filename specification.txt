│   └── error.js

```


**`uploads/` is NOT under `src/`.** It sits at the root of crystal-backend,
beside `src`, `sql` and `scripts`:

```
crystal-backend/
├── src/          the application
├── sql/          schema.sql and its numbered deltas
├── scripts/      check.js, the seed helpers, the mock image generator
└── uploads/      what people upload, and the generated placeholders
```

`src` is source that is written and committed; uploads are DATA that arrives
at runtime and is deliberately not committed (see .gitignore). Keeping them
inside `src` also meant nodemon watched a thousand image files and restarted
the server on every upload, and it put user-supplied files inside the tree a
build copies.

The location is `UPLOAD_DIR` in .env, resolved against the crystal-backend
root when it is relative.

**In the box is a specification group, not a section of its own.**

The product page used to carry a separate "In the box" band: one square
tile per boxed item, each showing a photograph. There is no photography
for boxed items and there is not going to be, so what it actually drew was
a row of empty grey squares with captions under them.

What is in the box is a list of words, so it belongs where the rest of the
words are:

```
group:        IN_THE_BOX
definition:   Box contents
value:        Crystal C9 Pro, USB-C cable, 120W fast charger,
              SIM ejector, Quick start guide, Protective case
compare:      never
```

It is never `compare_enabled`: a compare column lines two values up
against each other, and two different lists of box contents do not line up.

`product_accessories` is unchanged and remains the STRUCTURED copy of the
same thing - one row per item, with an image column for whenever artwork
does exist. The console edits that table; the sheet row is what the
storefront reads.

## product_images - a product OWN pictures, out of media_assets

media_assets is polymorphic: `(owner_type, owner_id)` with no foreign key,
because one column cannot point at five tables. That is the right shape for
artwork hanging off four different kinds of owner, and the WRONG shape for
the two runs that every single product has - there is no owner_type to
resolve, no chance of an id pointing into the wrong table, and no reason a
product own pictures should be unreachable by a join.

```
product_images

product_id    FK to products, ON DELETE CASCADE
kind          MAIN | ADVERT
device_type   desktop | mobile | all
file_path
alt_text
width / height
sort_order
is_deleted / created_at / updated_at
```

```
MAIN     the studio set - front, back, three quarter. The row of 1 to 3
         square images at the TOP of the product page.

ADVERT   the advertising run - full width marketing panels, each one a
         whole picture with its copy burnt into the artwork. Shown down
         the GALLERY TAB, 1 x n, butted together.
```

media_assets keeps what is genuinely polymorphic: section and series
banners, article figures, Crystal OS screens, and a product HERO and
THUMBNAIL slots.


**`purpose` decides where an asset appears, and the distinctions are load
bearing** - two of them were being confused, and the product page showed
the same photographs twice as a result:

```
HERO       the wide landing-page banner. Per device width.

THUMBNAIL  the listing tile.

GALLERY    an article figure, or a screen published with an OS release.
           A PRODUCT studio set is NOT here - see product_images.

BANNER     section and series artwork. Per device width.
```

The gallery tab shows DETAIL and falls back to GALLERY only when a product
has no advertising run at all, so a tab that would otherwise be empty still
shows something.

Tables:


## os_versions


```
id

version

title

description

highlights

cover_image

release_date
```


Example:

```
Crystal OS 5.2
```


`highlights` is free text, one bullet per line - which is what the
console writes into it. Structuring it would mean an editor could no
longer paste release notes straight in.

**A release also owns MEDIA**, as `media_assets` rows with
`owner_type = OS_VERSION`. Support / Crystal OS is a marketing page rather
than a changelog, and a wall of release notes is what a changelog looks
like - so every release leads with its cover image and is shown alongside
the screens published with it. `GET /api/support/os` returns them attached
to their release, in one query for the whole list.


---

## product_os_history


```
product_id

os_version           varchar - the DEVICE own version string

release_date         when THIS model received it

content              the notice, as prose

pub_approve_number   varchar

sort_order

is_deleted / created_at / updated_at
```


**THIS DOES NOT JOIN TO `os_versions`, and that is the point.**

It used to: a row said "release 5.2 reached the C9 Pro on this date", and
the name, the notes and the artwork all came from the release. The premise
was wrong. The firmware a television or a set-top box ships is not a Crystal
OS build at all, and even on the handsets the version a device reports is
its own - so a version could only be recorded against a device if somebody
first invented a matching `os_versions` row to point at.

`os_versions` is still the Crystal OS product page (Support / Crystal OS).
The two are simply not the same list, and nothing joins them.

The DATE is the date this model received the version, not the date the
version was released: a build reaches the flagship in March and the budget
line in June, and one date for both is what makes people think their device
has been forgotten.

# Repair Pricing


```

name

labour_minutes
```

Example:


```
Battery

40        sale_price      published counter price

15        service_price   published labour

CR-020-40 approval_no

1         limit_quantity
```


**THE PUBLISHED PRICE LIST, AND ONLY THAT.**

It used to carry the ticket side of a repair as well - the shelf item a line
consumed (`part_id`), its bench minutes, how many were covered per repair, an
internal costing price beside the counter one (`sale_price`), and a child
table of attached documents. All of that is the REPAIR's business rather than
the price list's, and `repair_ticket_items` already keeps its own copy of
every figure it charged - so an old ticket still shows the price it quoted.

What is left is the four things a customer reads:

```
part_name      which part, AS PUBLISHED. A plain string, deliberately not a
               link to `parts`: the price list names things the way a
               customer would recognise them, and the shelf names them the
               way a technician orders them.

part_price     what the part costs
service_price  what the labour costs
approval_no    the reference the figure was approved under. A free STRING,
               never arithmetic: the format differs by market.
```

`service_price_attachments` is REMOVED.


## The storefront price list is PAGED

```
GET /api/products/:slug/service-pricing?page=1&limit=10

returns { rows, total, page, limit }
```

A published price list is a document rather than a summary, and paging it
server-side is what stops the API sending sixty rows to draw ten.

## Primary colour: SKY BLUE. The app icons too.

```
brand.400   #38BDF8   the same hue lifted, for dark mode
brand.500   #0EA5E9   buttons, active menu items, focus rings
brand.600   #0284C7   hover
```

Deliberately NOT the storefront's orange. These are two tools for two
different people, and an operator with both open should be able to tell at
a glance which window they are typing into - which a shared layout and a
shared component library otherwise make surprisingly hard.

The favicon, the manifest and the `theme-color` meta carry the same ramp.


## A popover opened inside a dialog must render ABOVE it.

Chakra puts a popover panel inside a `.chakra-popover__popper` wrapper
whose theme style is `z-index: inherit`. Portalled to `<body>` that
inherits `auto`, while a modal's own container carries 1400 - so a select
or a date picker opened inside a form dialog renders UNDERNEATH it.

Fixed in two places, and both are needed:

```
rootProps={{ zIndex: 1500 }}   on the PopoverContent of SelectField
                               and DatePicker. A style PROP always beats
                               the component's __css, so this one cannot
                               lose.

.chakra-popover__popper        raised in styles/app.css, for any popover
  { z-index: 1500 }            those two files do not own. Cannot be
                               relied on ALONE: emotion injects Chakra's
                               `inherit` at render time, so which <style>
                               lands last is a race.
```

Both are asserted in `src/chrome72.test.js`.


## Row actions are ICON BUTTONS with a tooltip.

Edit and delete are the same two glyphs on every screen in the console,
and spelling them out on every row costs a column of width to say what the
icon already said. The label moves to a tooltip on hover.

```
default:      icon only, 36x36 hit area, label in the tooltip
opt out:      actionsIconOnly={false} - for a screen whose actions are
              not conventional enough to be recognised as a glyph
              ("Issue licence", "Reopen"), where the word IS the
              affordance
no icon:      keeps its label whatever the flag says
inline up to: 3 icon actions, or 2 if any of them is labelled or is a
              control the screen drew itself. Past that, the ... menu.
```

## The hero carousel

Modelled on mi.com/global. It carries a PLAY / PAUSE BUTTON for autoplay,
sitting at the end of the indicator row rather than parked beside it - so
it reads as the last item of the same instrument.

```
slides move as a TRACK, not a cross-fade
one indicator per slide; the ACTIVE one is a progress bar
play / pause at the end of the indicator row
arrows on hover, keyboard arrows when focused, swipe on touch
pauses on hover and while the tab is in the background
does not autoplay at all under prefers-reduced-motion
a single slide is a picture: no timer, no indicators, no arrows
```

**ONE CLOCK, NOT TWO.** The indicator fill IS the timer: it animates from
0 to 100% over the slide interval and the advance fires from its
`animationend`. A CSS animation for the bar plus a `setInterval` for the
advance is two clocks that drift apart, and every pause widens the gap
until the bar visibly finishes early or hangs full.

Pausing is therefore `animation-play-state: paused`, which stops the bar
and the advance together because the event simply never fires.

The visitor's own play/pause decision outranks the automatic pauses: a
deck paused by the button must not start running again when the pointer
moves away.

# Product Detail


Tabs, which are ROUTED sub-pages (`/products/:slug/:tab?`) rather than
in-place state - a specification sheet and a repair price list are things
people send each other links to:


```
Overview          the bare product url

Specification     including the In the box group

Gallery           the advertising run, 1 x n

Service Pricing   paged, with approval numbers and documents

OS History        this handset, not the release
```


## The top of the page: 1 to 3 main images. ALL CAROUSEL.

A carousel is for a deck of unrelated offers competing for one slot on a
landing page. A product page has ONE subject, and hiding two of its three
photographs behind a timer means a visitor is shown the back of the phone
only if they wait.

So the main images are laid out side by side - the same GALLERY shots, and
the same treatment, as the tile the visitor arrived from, which is also
what makes the two pages read as one journey.

```
1 image    one wide picture
2 images   two columns
3 images   three columns
below md   always stacked - three squares across a phone are thumbnails
object-fit contain, never cover: cropping a phone to fill a square is
           how the corners of it disappear
```


## NO BUY BUTTON.

Selling happens on the Crystal Eshop, which is a separate system this site
cannot complete a purchase in. A button that cannot buy anything is worse
than no button, because it is only discovered to be a link after it has
been trusted.

The price still travels with the sticky tab bar, so it stays readable half
way down the specification sheet. Comparison is the only action this page
can actually carry out, so it is the only one offered.


## Gallery tab: the ADVERTISING images, 1 x n, concatenated.

Not the phone's gallery photographs - those are the main images at the top
of the page, and showing them again behind a tab is the same four pictures
twice. These are the `DETAIL` assets: full width marketing panels, each
one a whole picture with its copy burnt into the artwork.

```
one column, full page width
each panel butted against the one above it - no gutter, no card
each panel keeps its OWN proportions - no fixed ratio, or the copy
  inside half of them is cropped off
no lightbox - at full width they are already at their intended size
```

A grid of two or three columns is what turned this into a wall of
thumbnails and made the copy inside each panel too small to read.


## Service pricing tab

```
columns:  part or service | sale price | service price | total
          | approval number | documents | covered per repair

paged:    10 a page, server side
```

See section 9, Repair Pricing, for why the sale price and the internal
part price are two different numbers.


## OS history tab

THIS HANDSET's history, which is a different question from what is in a
release - that is Support / Crystal OS. The one asked here is the one an
owner actually asks: "has my phone had it, and when?"

So the date shown is **the date this model received the version**, not the
version's own release date. A release reaches the flagship in March and
the budget line in June, and showing one date for both is what makes
people think their phone has been forgotten.

Each entry carries the release's cover image beside its notes - a
thumbnail rather than a band, because the subject of this page is the
phone and not the release.

# Full-Stack Content Integrity & Authenticity System

## 1. Project Context

I have a full-stack web application with:

* Backend: Node.js + Express.js
* Frontend: React
* Backend and frontend deployed on the same server
* Local filesystem storage for images
* Database for application data
* Admin-created notifications, FAQs, and feedback
* Hero images and product images

I need to implement a cryptographic content signing and verification system.

The objective is to ensure that content delivered by the backend can be verified by the frontend before it is rendered.

## 2. Main Requirements

Implement a reusable, production-oriented content signing system that supports:

1. Signing content on the backend.
2. Verifying signed content on the frontend.
3. Detecting image file modifications.
4. Supporting RSA and ECDSA signing algorithms.
5. Switching the signing algorithm through configuration.
6. Supporting key identifiers and key rotation.
7. Preventing unsigned or invalid content from being rendered by the normal React application.
8. Keeping private keys exclusively on the backend.

Do not use visible watermarks on images.

Do not use Sharp for watermarking. Sharp may be used for image validation or processing if required, but image integrity must be based on cryptographic hashing.

---

# 3. Content Types That Must Be Signed

The system must support the following content categories:

## 3.1 Hero Images

Sign all hero image assets.

Required metadata:

* ID
* Filename or asset identifier
* MIME type
* File size
* SHA-256 hash
* Signature
* Algorithm
* Key ID
* Schema version

## 3.2 Product Images

Sign every product image uploaded or registered in the system.

The same signing workflow must apply to:

* Main product images
* Additional product images
* Product gallery images
* Product thumbnails, if stored as independent files

If resized or converted image variants are served, clearly define whether each variant is independently signed or whether the system signs a source asset plus trusted transformation metadata.

Do not compare the hash of a source image against a transformed image file.

## 3.3 Notifications

Sign all admin-created notifications.

Required fields:

* ID
* Text
* Created timestamp
* Updated timestamp, if applicable
* Status or publication fields that are part of the signed content
* Signature metadata

If a notification is edited, it must be signed again. Old signatures must not remain valid for modified content.

## 3.4 FAQs

Sign all FAQ content.

Required fields:

* ID
* Question
* Answer
* Ordering or display metadata, if integrity-sensitive
* Created timestamp
* Updated timestamp, if applicable
* Signature metadata

Any modification to a signed FAQ must invalidate the previous signature.

## 3.5 Feedback

Clarify and implement the appropriate model for feedback:

* If feedback is created by users and displayed publicly, sign the backend-approved representation before delivery.
* If feedback is moderated or edited by admins, re-sign the final approved representation.
* Do not assume that a user-submitted signature proves administrative approval.
* Define whether feedback must be signed when created, when approved, or both.

The backend must not accept a user-supplied signature as proof of authenticity.

---

# 4. Cryptographic Algorithm Requirements

Support two configurable signing algorithms.

## Option A: RSA

* Key type: RSA
* Minimum key size: 3072 bits
* Signature algorithm: RSA-PSS with SHA-256
* Salt length: RSA-PSS standard salt length matching SHA-256 digest length (32 bytes)
* Hash: SHA-256

## Option B: ECDSA

* Key type: EC
* Curve: prime256v1 (P-256)
* Signature algorithm: ECDSA with SHA-256
* Signature encoding: IEEE P1363 for browser Web Crypto interoperability

Use Node.js built-in crypto APIs.

Do not implement cryptographic primitives manually.

The system must have a clear algorithm configuration, for example:

```env
CONTENT_SIGNING_ALGORITHM=ECDSA
CONTENT_SIGNING_KEY_ID=content-key-v1
```

Supported values:

```text
RSA
ECDSA
```

Use an explicit mapping between configuration values and cryptographic implementations.

Do not silently fall back to another algorithm if configuration is invalid.

Fail securely with a clear startup error.

---

# 5. X.509 Certificate Requirements

Use X.509 certificates to represent signing public keys.

The private key must remain on the backend.

The frontend must trust only explicitly configured public signing identities.

Requirements:

* Load private keys securely on the backend.
* Load the corresponding X.509 certificate.
* Extract and use the public key for verification.
* Validate that the configured certificate matches the expected signing identity.
* Support a key ID, such as `content-key-v1`.
* Support key rotation.
* Do not send private keys to the frontend.
* Do not accept arbitrary certificates supplied by API responses as trusted roots.

Important:

An X.509 certificate does not independently guarantee authenticity. The application must establish trust in the certificate or its public key.

For the initial deployment, implement a pinned public-key or certificate-based trust configuration suitable for the same-server React application.

Clearly document how trust is established and how the frontend bundle is updated during key rotation.

---

# 6. Canonical Payload Specification

The backend and frontend must sign and verify exactly the same bytes.

Do not independently serialize JavaScript objects using arbitrary formats without documenting the canonicalization behavior.

Implement a shared, deterministic payload serialization strategy.

Preferred approach:

* Define a versioned payload schema.
* Define required fields and field types.
* Define field ordering.
* Define how strings, Unicode, numbers, null, and timestamps are represented.
* Encode the canonical payload as UTF-8.
* Sign the UTF-8 bytes.

Example notification payload:

```json
{
  "schemaVersion": 1,
  "type": "notification",
  "id": "notification-123",
  "text": "Welcome!",
  "createdAt": "2026-09-16T10:00:00.000Z"
}
```

The signature must cover the complete canonical payload.

Do not sign only a subset of security-sensitive fields.

Do not sign rendered HTML instead of the structured data.

Prevent signature confusion by including a content type and schema version in the signed representation.

---

# 7. Signature Envelope

Use a consistent signature envelope for all signed content.

Example:

```json
{
  "content": {
    "id": "image-123",
    "filename": "image-123.png",
    "mimeType": "image/png",
    "size": 245678,
    "sha256": "hex-encoded-sha256"
  },
  "signature": {
    "algorithm": "ECDSA-SHA256",
    "keyId": "content-key-v1",
    "value": "base64-signature",
    "encoding": "ieee-p1363",
    "schemaVersion": 1
  }
}
```

For RSA-PSS, document the signature encoding and parameters explicitly.

The envelope must be validated before verification.

Reject:

* Missing signature
* Unsupported algorithm
* Unknown key ID
* Invalid schema version
* Invalid field types
* Invalid signature encoding
* Unexpected payload structure

Do not trust the algorithm name supplied by the client to select a different verification implementation.

The backend must use a trusted algorithm policy and the corresponding configured key.

---

# 8. Image Signing Workflow

When an image is uploaded:

1. Authenticate and authorize the uploader.
2. Validate the uploaded file.
3. Validate the actual file format rather than relying only on the client MIME type.
4. Decide the final stored representation.
5. Store the image on the local filesystem using a generated safe identifier.
6. Calculate SHA-256 from the exact final stored file bytes.
7. Create canonical signed image metadata.
8. Generate a digital signature with the configured signing key.
9. Store the image metadata and signature in the database.
10. Return signed metadata to the frontend.

No visible watermark is required.

Example image record:

```json
{
  "id": "image-123",
  "filename": "image-123.png",
  "mimeType": "image/png",
  "size": 245678,
  "sha256": "a1b2c3...",
  "signature": {
    "algorithm": "ECDSA-SHA256",
    "keyId": "content-key-v1",
    "value": "base64-signature",
    "encoding": "ieee-p1363",
    "schemaVersion": 1
  }
}
```

If an image is modified, replaced, or re-encoded, the hash should change when the file bytes change.

If the application intentionally transforms an image, it must generate and sign the final representation that the frontend will verify.

# 9. Image Storage Security

Images are stored locally on the server.

Requirements:

* Never trust a user-provided filename as a filesystem path.
* Prevent path traversal.
* Generate unique server-side filenames.
* Keep uploads outside sensitive application source directories where practical.
* Avoid exposing the upload directory through an uncontrolled static route.
* Use controlled image-serving routes.
* Restrict access where content is private.
* Validate file type and file size.
* Prevent unauthorized replacement of image files.
* Ensure metadata and file paths cannot be manipulated through user input.

Use a database record to map an image ID to its safe storage path.

Do not store arbitrary filesystem paths supplied by clients.

# 10. Backend Verification

The backend must also verify stored content integrity where appropriate.

Frontend verification is not a security boundary because users can modify browser JavaScript or bypass frontend rendering logic.

Implement backend verification for security-sensitive operations, such as:

* Serving protected assets
* Publishing content
* Administrative content updates
* Integrity audits
* Detecting unauthorized filesystem modifications

Do not assume that frontend verification prevents an attacker from accessing or displaying modified files through custom code.

# 11. Frontend Verification

Create reusable React verification utilities.

The frontend must:

1. Validate the signature envelope.
2. Check the algorithm against an allowed algorithm policy.
3. Resolve the key ID to a trusted public key or certificate.
4. Recreate the exact canonical payload.
5. Verify the digital signature.
6. For images, download the exact file bytes.
7. Calculate SHA-256 locally.
8. Compare the calculated hash with the signed hash.
9. Render the content only after verification succeeds.

Do not directly render unverified signed content through the normal secure components.

Do not create an image object URL until image integrity verification succeeds.

Do not use an API-provided public key as an automatically trusted key without an established trust mechanism.

# 15. Key Rotation

Implement key identifiers from the beginning.

Example:

```text
content-key-v1
content-key-v2
```

Requirements:

* New content uses the active signing key.
* Existing content remains verifiable using an authorized previous key.
* The frontend can trust multiple active/previous public keys during rotation.
* The backend rejects unknown or revoked key IDs.
* Document how old signatures are handled after key revocation.
* Do not delete old keys until all content signed with them has been migrated, expired, or otherwise handled according to a defined policy.

Do not silently replace a key while retaining the same key ID.
