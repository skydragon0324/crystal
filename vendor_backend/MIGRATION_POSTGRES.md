# Oracle 11g → PostgreSQL migration

Scope kept deliberately narrow: config + schema, minimal application code.
Node 12.22 / Express 4 / Knex 0.21.20 are unchanged.

## Why this was cheap

The app talks to the database through Knex, and Knex has a first-class `pg`
dialect. Nothing in `controllers/`, `routes/`, `middleware/` or `utils/` was
touched. The survey that made this possible:

| Oracle construct | Count | Outcome |
|---|---|---|
| `db.raw()` calls (all in `models/`) | 1,170 | mostly portable as-is |
| `TO_CHAR` | 560 | **no change** — pg supports the same format masks |
| `NVL` | 86 | **no change** — shimmed as a pg function |
| `.returning("*")` | 144 | **no change** — native in pg, better than Oracle |
| `SUBSTR`, `CONCAT`, `\|\|`, `FLOOR` | 274 | **no change** — compatible |
| `SYSDATE` | 16 | patched by script |
| `ROWNUM` | 1 | see open items |
| `MERGE INTO`, `CONNECT BY`, `DECODE`, `LISTAGG`, packages, procedures | 0 | none present |

The `DECODE` hits in the original grep were JavaScript (`jwt.decode`,
`base64decode`), not Oracle's `DECODE`.

## 1. Config — `db/knex.js`

The Oracle version is preserved as `db/knex.oracle.js.bak`.

Three things changed, one of them load-bearing:

**`client: 'oracledb'` → `client: 'pg'`**, and `DB_CONNECT_STRING` split into
`DB_HOST` / `DB_PORT` / `DB_NAME` (pg has no connect-string equivalent).

**`wrapIdentifier` was removed.** This is the one that would have broken
everything on the first query. The Oracle config forced every identifier to
uppercase because Oracle folds unquoted names that way. Knex's pg dialect wraps
identifiers in double quotes, and in Postgres a quoted `"USERS"` is a *different
object* from the `users` table the schema creates — you would get
`relation "USERS" does not exist` immediately. Postgres folds unquoted
identifiers to lower case, which is what the converted DDL uses, so no wrapping
is needed at all.

**pg type parsers were added.** `node-oracledb` returned `NUMBER` as a JS
number. `node-postgres` returns `BIGINT` and `NUMERIC` as **strings** to protect
precision. Without the parsers in the new config, every `row.user_pk === 1`
comparison silently returns false and every `+` becomes string concatenation —
a failure mode that produces wrong data rather than errors. If any ID or money
column can exceed 2^53, drop the parser for that type and handle it as a string.

`postProcessResponse` was kept. It's a no-op on the normal path (pg already
returns lower case) but still covers any hand-written `AS "SomeAlias"`.

**Pool size:** `max` dropped from 600 to 20. Oracle multiplexes; Postgres forks
a backend *process* per connection against a default `max_connections` of 100.
600 will be refused outright. If you genuinely need that concurrency, put
PgBouncer in transaction mode in front and keep the app pool small.

## 2. Dependencies

`oracledb@4.2.0` → `pg@8.7.3` in `package.json`. 8.7.3 is the safe choice for
Node 12.22; later 8.x lines assume newer Node. `db/oracledb.js` was a
reference-only file (already commented out in `app.js:96`) and is renamed to
`db/oracledb.js.reference`.

```bash
npm uninstall oracledb && npm install
```

Dropping `oracledb` also removes the Oracle Instant Client requirement from
your build and deploy images.

## 3. Schema — `sql_pg/`

Generated by `tools/oracle2pg.py` from `sql/` (originals untouched):

- 149 tables, 118 sequences, 26 indexes converted
- `VARCHAR2(n)` → `VARCHAR(n)`, `CLOB`/`NCLOB` → `TEXT`, `BLOB` → `BYTEA`
- `NUMBER(1..4)` → `SMALLINT`, `(5..9)` → `INTEGER`, `(10..18)` → `BIGINT`,
  bare `NUMBER` → `BIGINT`
- **`DATE` → `TIMESTAMP`**, not `DATE`. Oracle's `DATE` carries a time
  component; mapping it to pg `DATE` would silently truncate every timestamp
  in the system.
- Sequence `MAXVALUE 9999999999999999999` → `9223372036854775807`, since the
  Oracle value exceeds pg's `bigint`
- **116 of 120 triggers eliminated.** They were all the Oracle
  `BEFORE INSERT ... :NEW.pk := seq.NEXTVAL` idiom, which becomes a column
  default: `ALTER TABLE t ALTER COLUMN pk SET DEFAULT nextval('t_s')` plus
  `ALTER SEQUENCE t_s OWNED BY t.pk` so the sequence drops with the table.

Run order:

```bash
psql -f sql_pg/00_compat.sql          # NVL / NVL2 / dual shims
psql -f sql_pg/01_table_managers.sql  # ... then 02 .. 21 in numeric order
psql -f sql_pg/99_triggers_plpgsql.sql
```

`00_compat.sql` defines `NVL` as a real Postgres function. That is what keeps
all 86 call sites unedited rather than rewritten to `COALESCE`.

## 4. The only application code that changed

`tools/patch_models.py` touched 4 files in `models/` — 16 edits total, all
mechanical:

- **14 age expressions.** `TO_CHAR(SYSDATE,'YYYY') - TO_CHAR(birthday,'YYYY')`
  relies on Oracle implicitly casting text back to a number. In Postgres
  `text - text` is a hard error. Rewritten as
  `EXTRACT(YEAR FROM CURRENT_DATE) - EXTRACT(YEAR FROM birthday)`, which
  returns numeric, so the surrounding `FLOOR(.../10)*10` is unaffected.
- **2 bare `SYSDATE`** → `CURRENT_TIMESTAMP`. This one can't be shimmed:
  Postgres can't resolve a bare identifier as a zero-argument function call.

All 22 model files still parse (`node --check`).

## Open items before you cut over

**1. `ROWNUM` in `models/blogModel.js:748`.** One query does
`SELECT temp.*, ROWNUM FROM (...)`. Postgres has no `ROWNUM`; replace with
`ROW_NUMBER() OVER ()`. It's a single line but needs a look at whether the
column is used for pagination or just display.

**2. `sql_pg/archive.sql`** still holds Oracle-only constructs: anonymous
PL/SQL blocks with `COMMIT`, `DBMS_SCHEDULER.create_job`, and
`INTERVAL '1' YEAR`. The scheduled job needs `pg_cron` (or an external cron
hitting a function); the interval literal becomes `INTERVAL '1 year'`. This
file reads like design notes rather than deployed schema — confirm before
spending time on it.

**3. `sql_pg/partitioning.sql`** uses Oracle range partitioning with
`ALTER TABLE ... DROP PARTITION`. Postgres 11+ declarative partitioning is
close but the syntax differs (`PARTITION BY RANGE (col)` then separate
`CREATE TABLE ... PARTITION OF ... FOR VALUES FROM ... TO ...`, and
`DETACH PARTITION` to drop). Same caveat — looks like notes, not live schema.

**4. Data movement.** This covers schema and code only. For the rows
themselves, `ora2pg` is the standard tool and will read the same Oracle
catalog; point it at the existing DB for `COPY`-format data dumps. Sequences
need `setval()` to the current max after loading, or your first inserts will
collide on the PK.

**5. Sort order.** Oracle's default binary sort and Postgres collation-aware
sort disagree on mixed-case and non-ASCII text. Any `ORDER BY` over names will
come back in a different order. If that matters, create the database with
`LC_COLLATE=C` to match Oracle's behaviour, or accept the change.

**6. Empty string vs NULL.** Oracle treats `''` as `NULL`; Postgres does not.
Any code path that inserts an empty string and later checks `IS NULL` will
behave differently. Worth a targeted look at the validators in `middleware/`
before go-live — this is the classic source of post-migration surprises.

**7. Transaction semantics.** Oracle readers never block; Postgres MVCC is
similar, so this is usually fine. But Oracle's default isolation and
`propagateCreateError: false` combination has masked pool exhaustion in the
past — with `max` now at 20 rather than 600, watch for acquire timeouts under
load and tune deliberately.
